Before

Before building the demo, prepare Cursor with the Salesforce skills. These skills give the agent Salesforce-specific instructions so it can better understand projects, metadata, Agentforce, and deployment tasks.

1 - Define skills in Cursor

Run this command once to add the Salesforce skills to Cursor globally.

npx --yes skills add forcedotcom/sf-skills --agent cursor --global --copy --yes

2 - Verify skills

Run this command to confirm the skills were installed and are available to Cursor.

npx skills ls --agent cursor --global

Activities In Cursor

Cursor is used to generate the first version of the demo application. The goal is to give Cursor the script and the visual reference, then let it create a static React and Vite demo that can be reviewed before connecting the real agent.

In this part, the agent is acting like the developer. It reads the demo script, understands the target experience, creates the application structure, and runs the commands needed to check that the demo builds correctly.

  1. Go to GitHub and open the repository that contains the demo files.
  2. Click Code and copy the repository URL.
  3. Ask the Cursor agent to clone the repository, or run the clone command in the Cursor terminal.
  4. Create the Salesforce project that will hold related Salesforce work.
  5. Be sure to be in the same folder for Demo_Script.MD so Cursor can reference it.
  6. Instruct Cursor to create the demo app.

Clone the repository

Use the repository URL copied from GitHub.

git clone <repo-url>
cd <repo-folder>

Create the Salesforce project

Run this in the Cursor terminal when a new Salesforce project is needed.

sf project generate --name StampedeSalesforceProject

Prompt example to create the demo app

This is an example prompt used to instruct Cursor to plan and create the static demo from the script and style guide.

5 - Run commands

Install the app dependencies and build the app to make sure the generated demo works.

Open the local version and review the look, content, and flow before hosting it publicly.

Hosting Options

After the demo is built, it needs to be hosted somewhere with a public URL. That URL is what Salesforce uses when configuring the trusted domain for the embedded Agentforce chat.

We can use either Azure Static Web Apps or GitHub Pages. The sections below show the steps for each option.

Activities In Azure

Azure Static Web Apps was one hosting option explored for making the demo available through a public URL. A public URL is needed because Salesforce must trust the domain where the embedded chat runs.

  1. Go to + Create a resource.
  2. Search for Static Web App.
  3. Click on Create.
  4. Add:
    • Leave subscription as it is, and select a resource group.
    • Name: no spaces allowed, example StampedeWebChatAzureDemo.
    • Plan Type: Free.
    • Deployment Details: Other.
    • Be sure that on the tab Deployment Configuration there is Deployment Token selected.
  5. Click Review and Create.
  6. On the overview for the app copy: 
    URL: https://gray-hill-04379890f.7.azurestaticapps.net
  7. Go to the tab Manage deployment token and copy it.

Note: We were able to create one Static Web App. With the Azure account we had access to, we could only have one Static Web App using the Free SKU. We were not able to create a second Static App due to:

Build and deploy locally with the deployment token

After copying the deployment token from Azure, build the app locally and deploy the generated files to the Static Web App.

Using GitHub

GitHub Pages was used as the hosting option for the demo. The demo needs Pages so it can be accessed from a public URL. Pages on a public repo is free. Pages on a private repo requires a paid plan, so the test was done with a public repo.

  1. Recreate the new repo on my account to setup the Pages.
  2. Ask Cursor to configure the app to be hosted in GitHub Pages.
  3. The workflow deploys the app every time changes are pushed to main.

Activities In Salesforce Once We Have The URL Where We Will Host The App

Salesforce needs the public URL before the chat can be embedded. The URL is used as the trusted domain for the messaging channel and embedded service deployment.

  1. Add the GitHub site as a trusted URL: https://jmoraguerrero.github.io/.
  2. Create an agent and test it, or ask Cursor to create it.
  3. Create a new queue for the object Messaging Session, then add users and the agent.
  4. Configure an actual user on Omni-Channel. A human user needs to be connected so the agent can redirect if needed. If there is no human, the agent will not work.
  1. Go to Setup - Messaging Settings. This is where the web chat channel is created.
  2. Click on New Channel, then Next and select Enhanced Chat.
    • Enter a Name: StampedeDemoGithub.
    • Deployment Type: leave it as Web.
    • Domain will be the URL where the demo is hosted. For https://jmoraguerrero.github.io/StampedeGitHubDemo/ would be jmoraguerrero.github.io.
  3. For routing type, select Agentforce Service Agent, then select the agent and queue created before.
  4. Go to Setup - Embedded Service Deployments, then click New.
  5. Select Enhanced Chat. This connects the embedded deployment to the enhanced chat channel.
  6. Select Web. This means the chat will be embedded in a website.
  7. Enter a name and domain, then select the messaging channel created before and save.
  8. After it is created, go to Code Snippet and click Install. It is not installing anything, but it takes you to the code where we get the details to embed the agent in the demo.
  9. Copy the chat code snippet. The snippet contains the values needed by the app.

Omni-Channel Setup

Omni-Channel is the Salesforce feature that lets a human user receive work from the chat. In this demo, the work is a Messaging Session. If the Agentforce agent needs to redirect or escalate to a person, Omni-Channel needs to know which queue, routing rules, presence status, and user can receive that work.

How the pieces work together

  • Service Channel: tells Salesforce that Messaging Session is work that can be routed.
  • Routing Configuration: tells Salesforce how important the work is and how to choose the user who receives it.
  • Queue: groups the messaging work and the users who can receive it.
  • Presence Status: lets a user mark themselves available for messaging work.
  • Presence Configuration: controls how much work a user can receive and which statuses they can use.
  • Service Resource / User: makes the human user available as a resource for routing.
  • Omni-Channel Utility: adds the Omni-Channel widget to a Salesforce app so the user can go online.

1 - Enable Omni-Channel

  1. Go to Setup.
  2. Search for Omni-Channel Settings.
  3. Enable Omni-Channel.
  4. Save the settings.

2 - Create or confirm the Service Channel

The service channel tells Salesforce what object should be routed by Omni-Channel. For this demo, use Messaging Session.

  1. Go to Setup.
  2. Search for Service Channels.
  3. Create or confirm a service channel for Messaging Session.
  4. Save the service channel.

3 - Create the Routing Configuration

The routing configuration controls how Salesforce sends the messaging work to users. For a demo, keep it simple and use a basic priority and routing model.

  1. Go to Setup.
  2. Search for Routing Configurations.
  3. Create a routing configuration for messaging work.
  4. Set the priority and routing model.
  5. Save the routing configuration.

4 - Create the Queue

The queue is where the messaging work waits until Omni-Channel sends it to an available user.

  1. Go to Setup.
  2. Search for Queues.
  3. Create a queue for the Messaging Session object.
  4. Associate the queue with the routing configuration created before.
  5. Add the human users and the agent users that should be part of the demo.
  6. Save the queue.

5 - Create the Presence Status

Presence is how the user tells Salesforce if they are available. If the user is not available, Omni-Channel will not route messaging work to them.

  1. Go to Setup.
  2. Search for Presence Statuses.
  3. Create an available status for messaging, for example Available - Messaging.
  4. Add the Messaging Session service channel to the status.
  5. Save the presence status.

6 - Create or update the Presence Configuration

The presence configuration controls how much work a user can receive and which users can use Omni-Channel.

  1. Go to Setup.
  2. Search for Presence Configurations.
  3. Create or update the configuration used for the demo users.
  4. Set the capacity for the user.
  5. Add the available presence status created before.
  6. Assign the configuration to the right users or profiles.
  7. Save the presence configuration.

7 - Add presence access to the user or profile

The user must have access to the presence status. Without this, the user may open Omni-Channel but not see the status needed to go online.

  1. Go to the user profile or permission setup used by the demo user.
  2. Find Enabled Service Presence Status Access.
  3. Add the available messaging presence status.
  4. Save the change.

8 - Add Omni-Channel to the Salesforce app

The user needs the Omni-Channel widget in the Salesforce app. This is where they set themselves available and receive work.

  1. Go to Setup.
  2. Search for App Manager.
  3. Find the Salesforce app used for the demo and click Edit.
  4. Go to Utility Items.
  5. Click Add Utility Item.
  6. Select Omni-Channel.
  7. Save the app.

9 - Add the user as a Service Resource

The human user needs to be available as a resource so Salesforce can route messaging work to them.

  1. Go to Setup.
  2. Search for Service Resources.
  3. Create or confirm a service resource for the human demo user.
  4. Make sure the service resource is active.
  5. Save the service resource.

10 - Test Omni-Channel

  1. Open the Salesforce app used for the demo.
  2. Open the Omni-Channel utility.
  3. Set the user presence to the available messaging status.
  4. Start a chat from the hosted demo site.
  5. Confirm that the agent can route or escalate the messaging session to the available user.

Code Snippet Example

The code snippet is generated by Salesforce. We do not paste the whole snippet directly into the app. Instead, we copy the key values and use them as GitHub variables. 

<script type='text/javascript'>
  function initEmbeddedMessaging() {
    try {
      embeddedservice_bootstrap.settings.language = 'en_US'; // For example, enter 'en' or 'en-US'

      embeddedservice_bootstrap.init(
        '00DAs00000vvZeb',
        'StampedeGitHubDemo',
        'https://velocity-fun-8615--stampede.sandbox.my.site.com/ESWStampedeGitHubDemo1781103141367',
        {
          scrt2URL: 'https://velocity-fun-8615--stampede.sandbox.my.salesforce-scrt.com'
        }
      );
    } catch (err) {
      console.error('Error loading Embedded Messaging: ', err);
    }
  };
</script>
<script type='text/javascript' src='https://velocity-fun-8615--stampede.sandbox.my.site.com/ESWStampedeGitHubDemo1781103141367/assets/js/bootstrap.min.js' onload='initEmbeddedMessaging()'></script>
